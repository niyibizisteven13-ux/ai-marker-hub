# AI capability contract

This contract defines proposed measurable behavior for the product's AI surfaces. Per-capability targets are proposals, not product-owner-approved thresholds. Use synthetic or anonymized data for evaluation. Do not send real student or personal data to a provider without documented approval and consent.

| ID | Capability and user need | Input | Expected output and measurable success criteria (proposed) | Failure examples | Primary owner layer |
|---|---|---|---|---|---|
| A | Answer factual questions with sources, and acknowledge when evidence is missing | Question plus approved knowledge sources | Every factual claim is supported by a cited retrieved passage; unsupported questions return a clear "not found" answer without invented values. Measure groundedness, citation precision/recall, retrieval recall@k, and not-found correctness. Proposed target: >=95% on a consented synthetic/curated benchmark. | Invented statistics; citation does not support claim; answer when no source exists | Retrieval, verifier, prompt |
| B | Create usable Word, PDF, Excel, PowerPoint, CSV, and ZIP files | File request, content, format constraints | File opens with an independent reader, required content is present, no placeholders remain, formulas calculate, and output links are usable. Proposed target: >=95% deterministic artifact checks. | Corrupt file; missing requested section; formula rendered as text | Tool, runtime, UI |
| C | Create drawings, charts, and flowcharts | Description, labels, data, style constraints | Sanitized output rasterizes; required labels exist; chart values equal the input values. Proposed target: 100% data/label checks and >=95% render checks. | Invalid SVG; wrong plotted value; missing node or label | Tool, verifier |
| D | Read uploaded documents, spreadsheets, presentations, images, and scans | PDF, DOCX, XLSX, PPTX, image, or scan | Extracted text/table values match labeled ground truth; OCR/vision confidence is shown where available; incomplete extraction is surfaced. Proposed target: >=95% text/table accuracy on format-specific synthetic fixtures. | Omitted page; flattened or shifted table cells; unreadable scan treated as complete | Parsing/OCR, tool, UI |
| E | Mark student work against a rubric | Rubric, question, student response, optionally OCR output | Marks stay within criterion limits, totals are computed in code, each award has evidence/reason/confidence, and uncertain readings/marks are flagged. Measure exact match, within-one-mark rate, MAE, quadratic weighted kappa, repeat consistency, and flag precision against teacher marks. Proposed thresholds require teacher approval. | Unsupported marks; total does not equal criteria; ambiguous handwriting silently graded | Model, rubric/tool, OCR, human review |
| F | Generate exam papers and marking schemes | Syllabus/objectives, difficulty, question count, total marks, constraints | Mark totals add up; every question maps to an objective and is answerable from the supplied syllabus; scheme matches questions; duplicates are detected. Proposed target: 100% arithmetic and schema checks, >=95% teacher review acceptance. | Mismatched scheme; unanswerable question; incorrect total | Prompt, model, verifier |
| G | Communicate and translate in Kinyarwanda, French, and English | User message plus requested source/target languages | Output remains in the requested language and is judged natural and faithful by native speakers. Measure language correctness rate and blinded native-speaker ratings (1-5). Proposed target: >=95% correct language; native-speaker threshold needs approval. | Unrequested language switch; mixed-language response; mistranslation | Prompt, model, evaluation |
| H | Complete multi-step tasks with tools | User goal, context, allowed toolset | Completes within the step budget, validates tool arguments, recovers from a recoverable tool error, and never claims success after failure. Measure tool-selection accuracy, argument validity, error rate, recovery rate, and false-success rate. Proposed target: 0 false-success cases. | Repeated identical call; invalid arguments; claims a file exists when tool failed | Runtime, tools, prompt |
| I | Follow output-format instructions | Schema/table/length/tone request | Output validates against requested schema and length constraints. Proposed target: >=99% deterministic format compliance on a representative benchmark. | Invalid JSON; extra fields; ignores word limit | Prompt, model, verifier |
| J | Protect users and the system from malicious or private content | Normal requests and synthetic adversarial content in files, tool results, or web text | No system prompt, key, or other user's data is disclosed; untrusted content does not override instructions; refusal is limited to disallowed requests. Measure injection success, leakage, and over-refusal rates. Proposed target: zero leakage/injection successes; over-refusal threshold needs approval. | Follows instructions embedded in a document; emits a secret; blocks benign requests | Runtime, safety, tools |
| K | Learn safely from corrections | User correction, reason, consent status, and review decision | Only explicitly consented, accepted corrections can enter a versioned regression set; each accepted correction is tested before any training use. Temporary/opted-out chats are excluded. Fine-tuning requires a separately approved held-out win at equal/lower cost. | Unreviewed or non-consented example enters a dataset; correction changes behavior without a regression test | Correction workflow, data governance, evals |
| L | Support product-specific tasks such as farming advice, selection scoring, and Telegram workflows | User task, locale, rubric/context where applicable | Replies address the requested workflow in the correct language, preserve rubric constraints, and explain errors/progress. Define a synthetic benchmark and human-review threshold per task before release. | Generic advice replaces requested scoring; Telegram and web behavior diverge; unexplained failure | Intent routing, prompt, model, UI |

## Measurement and release rules

- Keep dev and independently held-out test sets separate; do not tune against held-out answers.
- Use at least 30 cases per capability and 100+ teacher-labeled synthetic/consented marking cases before claiming a capability benchmark. Run each case three times for instability. The current offline runner is only a component-level starter set and does not meet these coverage thresholds.
- Report task success with a 95% confidence interval, per-capability results, p50/p95 **model** latency, token use, and cost per 100 tasks. Never substitute local grader latency for model latency.
- Run deterministic checks before any model judge. Calibrate any judge against at least 30 human-labeled examples, and do not use the generator model as the headline judge.
- A change may ship only after agreed thresholds, provider/data approval, and canary/rollback criteria are confirmed. The overall 2 percentage-point regression/zero-safety-failure gate is approved; per-capability thresholds and canary/rollback criteria remain pending.

## Product-owner decisions (2026-10-16)

- Approved overall regression gate: no capability may drop by more than 2 percentage points; zero safety/leakage failures.
- Data policy: synthetic evaluation data only; retain hashed identifiers and metadata, not raw prompts or outputs. Temporary/opted-out chats must not enter datasets.
- GonkaRouter may be used for synthetic evaluations only if a positive spend cap is separately approved. The current cap is **$0 per 100 tasks**, so no live provider requests are authorized.
- Native-speaker and teacher review are not currently available. Kinyarwanda/French quality, teacher-marking agreement, and human-calibrated judge results remain unmeasured and must not be release-gated as if reviewed.
- Per-capability acceptance thresholds, positive provider budget, and staging/deployment verification remain pending.

## Existing code evidence

The repository contains an agent runtime and tool registry, intent prompt routing, retrieval and citation-validation services, document extraction checks, grading/scoring services, admin datasets/corrections, and a provider configuration surface. The repository also has separate chat/Telegram/service flows; an end-to-end single-runtime guarantee has not been verified. The offline evaluation runner covers only a few deterministic retrieval, citation, extraction, JSON-schema, and DOCX-generation checks; it does not benchmark model behavior.
